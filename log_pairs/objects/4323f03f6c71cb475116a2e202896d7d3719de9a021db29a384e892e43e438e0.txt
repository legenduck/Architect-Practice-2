# 브랜치·커밋 규칙

## 1. 브랜치

| 브랜치 | 용도 |
|---|---|
| `main` | 배포 가능한 상태. 직접 푸시 금지 |
| `feature/ISSUE-<번호>-<요약>` | 기능 개발. 예: `feature/ISSUE-142-coupon-checkout` |
| `fix/ISSUE-<번호>-<요약>` | 버그 수정 |
| `hotfix/<버전>` | 운영 긴급 수정. `main`에서 분기 |

## 2. 커밋 메시지

```
<타입>: <요약 (한국어 50자 이내)>

<본문: 무엇을 왜 바꿨는지>

Refs: ISSUE-<번호>
```

타입: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`

예:
```
fix: 절사를 모든 할인 적용 후 한 번만 하도록 수정

감면 전에 절사하던 순서 때문에 HJ-02 정산 금액이 달랐다.
요금 규정 제10조(v3.0)에 맞춘다.

Refs: ISSUE-118
```

## 3. 머지
- PR은 스쿼시 머지합니다. 스쿼시 커밋 메시지도 위 형식을 따릅니다.
- 머지 후 기능 브랜치는 삭제합니다.

## 4. 릴리즈
- 버전은 SemVer를 따릅니다. 요금 계산 결과가 바뀌는 변경은 최소 마이너 버전을 올립니다.
- 태그 `v<버전>`을 달고 `CHANGELOG.md`의 `Unreleased`를 해당 버전으로 옮깁니다.
